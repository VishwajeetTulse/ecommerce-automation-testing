% ---------------- Abstract ----------------
\begin{center}{\large\bfseries ABSTRACT}\end{center}
Every change to a web application risks breaking features that already worked. Running the same manual test cases again after every change is slow and error-prone, which is why stable and repeatable test cases are automated. This project builds an automated regression test suite for Swag Labs (\url{https://www.saucedemo.com}), a public demo e-commerce website with login, product catalogue, shopping cart and checkout, using Selenium WebDriver driven from Python with the pytest framework.

The passing test cases from the companion manual testing project were selected for automation. The suite is organised with a simple Page Object Model: four small classes (LoginPage, InventoryPage, CartPage, CheckoutPage) hold the element locators and user actions of each page, so that tests read like user stories and locator changes are confined to one file. A pytest fixture starts a fresh headless Microsoft Edge browser for every test and closes it afterwards; a hook captures a screenshot whenever a test fails and embeds it in a self-contained HTML report produced by pytest-html. Parametrisation runs the same login and checkout validation logic with several data sets, and a known defect of the \texttt{problem\_user} account is kept in the suite as an expected failure.

The final suite contains 22 tests across five modules (login, products, cart, checkout, navigation). A full run in headless Edge takes about 105 seconds and the latest execution reports 21 passed and 1 expected failure. The project demonstrates locator strategies, explicit waits, fixtures, data-driven tests, reporting and failure diagnosis, which are the core skills of Selenium-based test automation.

\section{Problem Statement Definition}\label{sec:ps}
Design and implement an automated functional regression test suite for an e-commerce website (Swag Labs) using Selenium WebDriver, covering login, product listing and sorting, shopping cart, checkout and navigation, with reusable page objects, data-driven test cases, automatic screenshots on failure and an HTML execution report, so that the whole regression run needs no human interaction.

% ---------------- 2 ----------------
\section{Software Requirements Specification}\label{sec:srs}
\subsection{Introduction}\label{sec:srs1}
Selenium WebDriver is an open-source tool that controls a real web browser from a program. A test script written in Python tells the browser to open a URL, find elements on the page (by ID, class name, CSS selector or XPath), type text, click buttons and read what is displayed. Assertions then compare what the page shows with what is expected. pytest is a Python testing framework that discovers test functions, provides fixtures for setup and teardown, supports data-driven tests through parametrisation and, with the pytest-html plugin, writes an HTML report. In this project these tools are used to automate the regression test cases of the Swag Labs online store.

\subsection{Scope}\label{sec:srs2}
\textbf{In scope:} functional tests of login (positive and negative), product listing and sorting, cart operations, checkout validation and totals, order completion, logout and protected-page access, in Microsoft Edge (Chrome supported through a command-line option).

\textbf{Out of scope:} visual or pixel comparison, performance measurement, mobile browsers, and tests of the deliberately broken users except one documented expected failure.

\subsection{Requirements}\label{sec:srs3}
Software requirements are:
\begin{itemize}[nosep]
  \item Windows 11 (Linux and macOS are also supported)
  \item Python 3.14
  \item Selenium 4.51 (Python bindings); Selenium Manager downloads the browser driver automatically
  \item pytest 9 and pytest-html 4
  \item Microsoft Edge 142 or Google Chrome
  \item Visual Studio Code (any editor), Git and GitHub
  \item Internet connection to \url{https://www.saucedemo.com}
\end{itemize}
Hardware: any computer with a 2 GHz dual-core processor and 4 GB RAM.

\section{System Implementation}\label{sec:impl}
\subsection{Technologies}\label{sec:impl1}
\textbf{Python} is the scripting language used for the tests. It is simple to read, has official Selenium bindings and a very popular test framework (pytest), so the whole suite is short and easy to explain.

\textbf{Selenium WebDriver} provides the browser automation. The script creates a driver object (\texttt{webdriver.Edge}), navigates with \texttt{driver.get(url)}, locates elements with \texttt{find\_element(By.ID, "login-button")} and interacts through \texttt{send\_keys()} and \texttt{click()}. Waits (\texttt{implicitly\_wait}, \texttt{WebDriverWait}) make the script wait for the page instead of using fixed sleeps.

\textbf{pytest} discovers every function whose name starts with \texttt{test\_}, runs the fixture that gives it a browser, executes the assertions and records pass or fail. \texttt{@pytest.mark.parametrize} runs one function with several data sets; \texttt{@pytest.mark.xfail} marks a test that is expected to fail because of a known defect.

\textbf{pytest-html} writes a single self-contained HTML report with the result and duration of every test; screenshots of failed tests are embedded in it.

\textbf{Page Object Model} is a design pattern in which one class represents one page of the application. The class holds the locators of that page and methods for the user actions. Tests call these methods instead of using raw locators, so if the site changes only the page class has to be updated.

\subsection{Working of Selenium WebDriver}\label{sec:impl2}
Selenium WebDriver works as a client-server system. The Python test is the client. It sends commands (open URL, find element, click, get text) over HTTP to a small server program called the browser driver (\texttt{msedgedriver} for Edge, \texttt{chromedriver} for Chrome) using the W3C WebDriver protocol. The driver translates each command into native browser actions and sends back the result. Selenium 4 includes Selenium Manager, which downloads the driver matching the installed browser version automatically, so no manual driver setup is needed.

The driver fixture gives every test a fresh browser:
\begin{lstlisting}[language=Python]
@pytest.fixture
def driver(request):
    options = webdriver.EdgeOptions()
    if not request.config.getoption("--headed"):
        options.add_argument("--headless=new")
    options.add_argument("--window-size=1280,900")
    drv = webdriver.Edge(options=options)
    drv.implicitly_wait(5)
    yield drv
    drv.quit()
\end{lstlisting}

The LoginPage page object:
\begin{lstlisting}[language=Python]
class LoginPage:
    USERNAME_INPUT = (By.ID, "user-name")
    PASSWORD_INPUT = (By.ID, "password")
    LOGIN_BTN = (By.ID, "login-button")
    ERROR = (By.CSS_SELECTOR, "h3[data-test='error']")

    def login(self, username, password=DEFAULT_PASSWORD):
        self.driver.find_element(*self.USERNAME_INPUT).send_keys(username)
        self.driver.find_element(*self.PASSWORD_INPUT).send_keys(password)
        self.driver.find_element(*self.LOGIN_BTN).click()
        WebDriverWait(self.driver, 10).until(
            lambda d: "inventory.html" in d.current_url or d.find_elements(*self.ERROR))
        return InventoryPage(self.driver)
\end{lstlisting}

\subsection{Automated Test Cases}\label{sec:work2}
A data-driven negative login test and the checkout totals test:
\begin{lstlisting}[language=Python]
@pytest.mark.parametrize("username,password,expected", [
    ("", "", "Username is required"),
    ("standard_user", "", "Password is required"),
    ("standard_user", "wrong", "do not match any user"),
    ("locked_out_user", "secret_sauce", "locked out"),
])
def test_invalid_login_shows_error(login_page, username, password, expected):
    login_page.login(username, password)
    assert expected in login_page.error_message()

def test_overview_totals_are_correct(checkout):
    checkout.fill_information("Vishwajeet", "Tulse", "411041")
    subtotal, tax, total = checkout.subtotal(), checkout.tax(), checkout.total()
    assert subtotal == pytest.approx(39.98)
    assert tax == pytest.approx(round(subtotal * 0.08, 2))
    assert total == pytest.approx(subtotal + tax)
\end{lstlisting}

\section{Advantages and Limitations}\label{sec:adv}
\textbf{Advantages}
\begin{itemize}[nosep]
  \item The complete regression suite runs unattended in about two minutes instead of about two hours by hand.
  \item Tests are repeatable and give the same result every time; no human error.
  \item Page objects keep locators in one file, so maintenance after a site change is small.
  \item Data-driven tests cover several inputs with one function.
  \item Failures are easy to diagnose because a screenshot and an HTML report are produced automatically.
  \item The suite can be plugged into a CI pipeline such as GitHub Actions.
\end{itemize}
\textbf{Limitations}
\begin{itemize}[nosep]
  \item Writing the scripts needs programming effort before the first benefit is seen.
  \item Automated tests only check what they are told to check; they do not notice new visual or usability problems.
  \item Scripts break when the application's DOM changes and must be maintained.
  \item Timing issues (page not yet loaded) can cause flaky results if waits are not used correctly.
  \item Only Edge and Chrome on desktop are covered.
\end{itemize}

% ---------------- 6 ----------------
\section{Conclusion}\label{sec:concl}
This project automated the regression test cases of an e-commerce website with Selenium WebDriver, Python and pytest. A small Page Object Model keeps locators out of the tests, fixtures give every test an isolated browser, parametrisation covers several data sets with one function, and an HTML report with automatic screenshots makes failures easy to diagnose. The final suite of 22 tests runs unattended in under two minutes and passes except for one documented defect kept as an expected failure. During development the screenshot-on-failure feature immediately revealed a scripting mistake in the login page object, showing the value of good diagnostics. In future the suite can run in a continuous-integration pipeline on every commit, be extended to Selenium Grid for cross-browser runs, and be linked to a test-management tool for traceability to the manual test cases.
